# 使用与索引格式

## 1. 安装与更新

安装链接：

```text
github:Lyshick/Lyshick-dsh-plug#path:plugins/dsh-spec-inspect
```

CLI：

```sh
dsh plugin install "github:Lyshick/Lyshick-dsh-plug#path:plugins/dsh-spec-inspect"
```

更新流程：

1. 修改 `package.json` 的 `version`；
2. 提交并推送；
3. 在目标机器的插件管理页先卸载旧版，再用同一链接安装；
4. 刷新页面；如果右上角入口没出现，重启一次 DSH（见 [踩坑与排查.md](踩坑与排查.md) 的客户端模块缓存一节）。

## 2. 打开与使用

1. 打开任意会话（**新会话、还没发消息也可以**）；
2. 点击会话右上角的「规范检视」图标（位于右侧边栏开关左侧；**空会话、还没发消息时也在同一位置**）；
3. 右侧边栏打开「规范检视」页；
4. 第一次使用点「设置」，填入索引 JSON 的 URL，点「保存并加载」；
5. 在「渠道」「规范文档」两个下拉列表里选择；
6. 点「开始检视」；
7. AI 在当前会话中开始检索工作区，并按规范文档的级别输出报告；
8. 报告生成后会自动出现在面板下方，按级别列出问题（见下面“结果面板”）。

索引或文档有更新时，点标题右侧的刷新图标即可重新拉取索引，不需要打开设置。刷新会保留当前渠道和文档选择。

页面会记住插件自己的索引源，但不会记住“上次选了哪个文档”；每次打开默认选第一个渠道的第一篇文档。

### 结果面板

检视完成后，面板下半部分按 `P0/P1/P2…` 分组列出问题：

- 点问题标题展开/收起详情：问题、原因、规范依据、风险、修复建议；
- **定位**（标题右侧「定位」按钮）：在右侧栏的文件预览里打开对应文件并高亮行号；
- **应用修复**（标题右侧「应用修复」按钮）：把这一条问题的位置、依据与修复建议作为指令发给当前会话的 AI，由 AI 修改代码；发送成功后按钮变成淡绿色的「已修复」勾标签，不能重复点击，刷新页面后状态仍然保留；报告区顶部同时出现“已发送修复请求”卡片，点“查看指令”可以展开实际发送的完整内容；
- 某条问题没有路径或没有修复建议时，对应按钮不可用；
- 报告来自会话事件日志：刷新页面或重新打开面板仍会显示最近一份结果；点“重新读取结果”可手动重试，检视还在进行时也可以点。

## 3. 设置

| 项 | 说明 |
|---|---|
| 索引源 URL | 一个可 HTTP(S) 访问的 JSON 文件 |
| 保存位置 | `$DSH_HOME/spec-inspect.json`，未设置时 `~/.dsh/spec-inspect.json` |
| 生效方式 | 保存后立即生效，不需要重启 Host |
| 刷新索引 | 标题右侧的刷新按钮：绕过 60 秒缓存重新拉取，保留当前选择；也可以点设置里的“重新加载索引” |
| 回退 | 如果 JSON 文件里没有 `indexUrl`，使用 Loader 行的 `config.indexUrl` |

设置文件内容示例：

```json
{
  "indexUrl": "https://spec.example.com/index.json",
  "applied": {
    "session-bbb8ec2b-…|js/game.js|2|4|修复建议前 160 字符": 1792995538767
  }
}
```

`applied` 是插件在“应用修复”成功后记录的已修复标记（值是该条修复的时间戳），用于刷新页面或重启后在报告里继续显示“已修复”。手动编辑时可以删掉它，不影响索引源。`cordis.patch.yml` 里的 `indexUrl: ''` 只是首次安装的默认值；用户在页面里保存的地址优先。重装插件后设置文件仍在。

## 4. 索引 JSON

### 4.1 推荐结构

```json
{
  "channels": [
    {
      "id": "web",
      "name": "Web 渠道",
      "docs": [
        {
          "id": "html-style",
          "title": "HTML 编写规范",
          "url": "https://spec.example.com/web/html-style.md"
        },
        {
          "id": "activity-page",
          "title": "活动页规范",
          "url": "https://spec.example.com/web/activity.doc",
          "type": "doc",
          "description": "活动页、抽奖、领奖类需求"
        }
      ]
    },
    {
      "id": "mini-app",
      "name": "小应用渠道",
      "docs": [
        {
          "id": "mini-app-style",
          "title": "小应用 HTML 规范",
          "url": "https://spec.example.com/mini-app/style.docx"
        }
      ]
    }
  ]
}
```

### 4.2 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `channels[]` | 是 | 渠道列表 |
| `channels[].id` | 否 | 渠道 id；缺省按顺序生成 |
| `channels[].name` | 否 | 渠道显示名；缺省用 id |
| `channels[].docs[]` | 是 | 该渠道的文档列表 |
| `docs[].id` | 否 | 文档 id；缺省从标题生成，用于 `/start` 定位 |
| `docs[].title` | 否 | 显示标题；缺省用 URL 文件名 |
| `docs[].url` | 是 | 文档地址，绝对 URL 或相对索引源的路径 |
| `docs[].type` | 否 | `md` / `doc` / `docx` / `txt` / `html`；缺省按 URL 后缀判断 |
| `docs[].description` | 否 | 副标题/备注；显示在下拉菜单里，选中后也会在下方补一行说明 |

### 4.3 兼容写法

索引解析器接受这些等价写法：

```json
["https://spec.example.com/a.md", "https://spec.example.com/b.doc"]
```

```json
{
  "docs": [
    { "title": "A", "href": "https://spec.example.com/a.md" }
  ]
}
```

```json
{
  "channels": {
    "web": {
      "name": "Web",
      "documents": [
        { "title": "A", "link": "/specs/a.md" }
      ]
    }
  }
}
```

```json
{
  "web": {
    "files": [
      { "title": "A", "path": "a.md" }
    ]
  }
}
```

- 相对路径会按索引源 URL 解析；
- 非 HTTP(S) 或无法解析的文档会被跳过，并显示在“索引提示”里；
- 文档 id 在同一渠道内重复时会自动加后缀，不会互相覆盖。

### 4.4 索引的最小示例

```json
{
  "channels": [
    {
      "id": "web",
      "name": "Web 渠道",
      "docs": [
        { "id": "html-style", "title": "HTML 编写规范", "url": "https://spec.example.com/web/html-style.md" }
      ]
    }
  ]
}
```

## 5. 文档类型

| 后缀 | 处理方式 |
|---|---|
| `.md` / `.markdown` | 按纯文本/Markdown 读取 |
| `.txt` | 按纯文本读取 |
| `.html` / `.htm` | 去脚本、去样式、去标签后读取 |
| `.docx` | 内置 zip + WordprocessingML 解析 |
| `.doc` | 内置 OLE + Word 97-2003 分片表解析；误标为 docx/RTF/HTML/纯文本时自动回退 |

不支持 PDF、Excel、PPT；扫描件、加密 Word 文档无法提取文字。

## 6. P0-P5 约定

插件本身不定义业务级别，只约束模型“按文档来”：

1. 文档定义了 P0-P5 的全部级别 → 按 P0 到 P5 分组；
2. 文档只定义了部分级别（例如只定义 P0-P3）→ 只输出已定义的级别；
3. 文档完全没有定义 P 级 → 使用 P0（阻断）/ P1（严重）/ P2（一般）；
4. 不允许模型自行新增、改名、合并或拆分级别；
5. 每个级别没有问题写“无”，不为了凑格式编造问题；
6. 无法从代码确认的疑点放“待确认”。

> 当前内部 `web-check` 示例文档定义的是 P0-P3，所以对它检视时不会出现 P4/P5 段落，这是预期行为。

## 7. 输出格式

提示词要求固定结构：

```markdown
## 检视结论
……

## 检视范围
场景：……
范围：……
说明：……

## P0 问题
- **位置**：`path:line`
- **问题**：……
- **规范依据**：……（引用文档原文）
- **风险**：……
- **修复建议**：……

## P1 问题
……

## 级别汇总
| 级别 | 数量 |
| --- | --- |
| P0 | 0 |
| P1 | 2 |

## 待确认
……
```

“检视范围”会说明实际检索了哪些目录/文件类型，以及依据的规范渠道与文档标题。

## 8. 一个完整的使用例子

索引：

```json
{
  "channels": [
    {
      "id": "web",
      "name": "Web 渠道",
      "docs": [
        { "id": "html-style", "title": "HTML 编写规范", "url": "https://spec.example.com/web/html-style.md" }
      ]
    }
  ]
}
```

操作：

1. 设置索引源为 `https://spec.example.com/index.json`；
2. 在「渠道」下拉选「Web 渠道」，在「规范文档」下拉选「HTML 编写规范」；
3. 点「开始检视」；
4. 当前会话收到一条用户消息，内容包含规范全文和检视要求；
5. 模型用 `glob` / `grep` / `read` 检索工作区，输出 P0-Px 报告。

## 9. 卸载与回滚

1. 在插件管理页卸载 `dsh-spec-inspect`；
2. 或从 profile 的 `package.json` 的 `dsh.profile.bundles` 移除 `dsh-spec-inspect`；
3. 可选：删除 `~/.dsh/spec-inspect.json`（会丢失索引源设置）；
4. 刷新页面。

插件不修改工作区代码，回滚不需要还原代码。
