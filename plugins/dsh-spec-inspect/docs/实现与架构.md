# 实现与架构

## 1. 插件形态与加载

这是一个 **bundle 包**，同时提供 Host 与 Client 两半：

```json
{
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "platform": "web",
      "immediately": true,
      "inject": [
        "@deepseek-ai/dsh-client-ui-conversation",
        "@deepseek-ai/dsh-client-ui-sidebar-right",
        "@deepseek-ai/dsh-client-locale"
      ]
    }
  }
}
```

- `dsh.bundle.patch` 让插件管理器在 profile 的 Loader 里插入 `spec-inspect` 行：

  ```yaml
  - insert:
      - id: spec-inspect
        name: dsh-spec-inspect
        config:
          indexUrl: ''
  ```

- `dsh.client.immediately: true` 是必需的。客户端插件默认惰性：脚本执行只注册 factory，模块体在第一次被 import 或物化时才运行。没有这一项，`apply` 不执行、slot 不注册，表现就是“插件已加载但 UI 上什么都没有”。
- `dsh.client.inject` 只控制客户端插件的激活顺序。这里依赖会话、右侧栏和 locale 三个包先就位。

Client 入口是 `./client`，对应 `client.js`；Host 入口是 `.`，对应 `index.js`。

## 2. Host / Client 分工

| 事情 | 放在哪 | 原因 |
|---|---|---|
| 拉取索引 JSON | Host | 内网地址、超时、大小限制、跨域都不该由浏览器处理 |
| 拉取并解析规范文档 | Host | Word `.doc` / `.docx` 需要 Node 的 zip、OLE、Buffer 能力 |
| 保存索引源 URL | Host | 写 `~/.dsh/spec-inspect.json`，不依赖浏览器存储 |
| 唤醒当前会话 Agent | Host | `ctx.agents.get(sessionId).followup(...)` 是 Host 能力 |
| 右上角入口（有内容 / 空白会话两处）、右侧栏 Tab | Client | Slot / Tab 注册必须发生在浏览器页面 |
| 选择渠道、文档、设置表单 | Client | 纯视图交互 |

Client 不直接读取工作区、不解析 Word，也不自己拼提示词；它只把用户的选择通过同源 HTTP 交给 Host。

## 3. Host 端

### 3.1 入口与状态

`apply(ctx, config)` 在插件激活时：

1. 读取 `~/.dsh/spec-inspect.json` 里的 `indexUrl`；
2. 如果文件里没有，回退到 Loader 行 `config.indexUrl`；
3. 用闭包 `state` 保存当前索引源；
4. 注册 `/spec-inspect` 前缀路由；
5. 建立按 URL 失效的索引缓存。

### 3.2 HTTP 路由

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/spec-inspect/status` | 当前索引源、设置文件路径、版本、是否已配置 |
| GET | `/spec-inspect/index?refresh=1` | 拉取并归一化索引，返回渠道与文档 |
| POST | `/spec-inspect/settings` | 写入 `{ indexUrl }` |
| POST | `/spec-inspect/start` | 写入 `{ docId, sessionId }`，拉文档、拼提示词、唤醒 Agent，返回 `startSeq` |
| GET | `/spec-inspect/report?sessionId=…&sinceSeq=…` | 读取会话事件日志里的最近一份检视报告并解析 |
| POST | `/spec-inspect/apply` | 写入 `{ sessionId, item }`，把一条修复建议发给该会话 Agent |

所有响应统一为：

```json
{ "ok": true, "value": { ... } }
```

或：

```json
{ "ok": false, "error": { "code": "no_session", "message": "……" } }
```

业务错误也返回 HTTP 200，由页面读取 `ok/error` 展示；只有路由不存在返回 404。这样浏览器端只需处理一种 JSON 形状。

### 3.3 `/start` 的完整流程

```text
1. 校验 docId / sessionId
2. ctx.get('agents').get(sessionId)
3. readIndex(false) 或 readIndex(true)
4. findDoc(index, docId)
5. httpGet(doc.url)（16 MB / 30 s 上限）
6. documentText(bytes, doc.type, doc.url)
7. buildPrompt({ channel, doc, text })
8. session.seq → startSeq（本次检视的起始事件序号）
9. agent.followup(userMessage(prompt))   // 完整 UserMessage：id / role / content / source
10. 返回 { title, channel, docId, chars, startSeq }
```

`userMessage()` 必须提供 `id` 与 `role`：`Agent.followup` 只是把对象放进 inbox，loop 在 step 时原样 `session.append('user/message', message)`，不会补这两个字段。Chat 的消息投影按 `event.data.id` 认领消息，缺 id 的 user 事件会在界面上被静默跳过（详见 [踩坑与排查.md](踩坑与排查.md) 第 18 节）。

关键点：

- **先找 Agent 再拉文档**：找不到会话时直接返回 `no_session`，不会白拉一份 16 MB 的文档。
- 索引找不到文档时先强制刷新一次索引，再报 `doc_not_found`，避免 60 秒缓存导致刚加的文档不可见。
- 发消息使用官方 `Agent.followup` 形状，不自己构造 `Message`（不需要 `createUserMessage`，也不需要 `id` / `role`）。
- 只发一条用户消息，不写自定义 Session 事件；因此不会污染会话日志，也不会触发“未知事件类型导致整份日志拒读”的问题。

### 3.4 索引缓存

- 缓存键是 `indexUrl`，60 秒有效。
- 设置保存后 `state.indexUrl` 变化，旧缓存自动不再命中。
- `?refresh=1` 和“重新加载索引”绕过缓存。
- 索引上限 4 MB，超时 20 秒。

### 3.5 检视报告读取与解析

`/report` 从会话的事件日志里取最近一份检视报告，不额外写任何事件：

```text
session = ctx.get('sessions').get(sessionId)
events  = session.snapshotEvents(sinceSeq ?? 0)
逐条找 type === 'assistant/message'
拼 message.content 里的 text 块
命中 '## P0' / '## 检视结论' / '## 级别汇总' 后调用 parseReport
取最后一条命中的消息 → { state: 'ready', groups, conclusion, scope, finishedAt, seq }
否则 → { state: 'pending' }
```

- `sinceSeq` 是 `/start` 返回的起始事件序号，轮询时只扫描本次检视之后的事件；不传则从头找最近一份报告（页面重新打开时用）。
- `parseReport` 是纯函数，导出给离线自检；它容忍模型输出的常见差异：
  - 标题 `## P1 问题`、`### **P2 问题**`、`**P1 问题**`；
  - 字段 `- **位置**：` / `- 位置：` / 全角或半角冒号；
  - 额外字段（`分类`、`原因`、`影响`）和分段（`P1 问题（第一部分）`）；
  - 位置写法 `js/game.js:124-140`、`` `src/a.vue:12` ``、带括号说明。
- 条目边界：`分类` 再次出现、或 `位置` 在已有位置后再次出现，都会开启新条目；其余字段和续行归入当前条目。
- 只有出现级别标题或报告章节标题才认定为报告；普通回答返回 `undefined`，页面不会被非报告文本污染。
- 级别分组按出现顺序聚合，同级多个分段会合并到同一个组。

### 3.6 应用修复建议

`/apply` 只做一件事：把一条问题作为修复指令发给当前会话的 Agent。

```text
buildFixPrompt(item):
  位置：`path:line[-endLine]`
  问题 / 原因 / 规范依据 / 风险
  修复建议：<fix>
  要求：先读相关上下文，只做必要修改，保持现有风格，不改无关文件，改完说明每个改动点
```

- 校验 `path` + `line`，并要求 `fix` 非空；缺任何一项返回 `bad_fix_target` / `no_fix`，不会发消息。
- 指令超过 20 000 字符返回 `too_large`。
- 发送仍然走 `agent.followup`，因此修改代码发生在正常的会话回合里：权限、审批、工具调用都由宿主负责。插件自身依旧不写工作区文件（唯一的持久化写入仍是设置文件）。
- 同一会话正在跑上一轮时，`followup` 可能被宿主拒绝；错误会原样显示在页面上。
- 发送成功后，Host 在内存里记下这条修复的身份 `fixKey = sessionId|path|line|endLine|fix 前 160 字符`，并把整个 `applied` 映射写入设置文件；`/report` 返回条目时附上 `applied: true`。这样页面刷新、重新读取报告、甚至重启 DSH 后，该条仍显示为“已修复”，不会又变回可点击。记录上限 300 条，超出按时间删除最早的一条。
- `/apply` 的响应同时返回 `prompt`（实际发给 Agent 的完整指令）。页面的报告区会显示一条“已发送修复请求 · 位置”的卡片，点“查看指令”展开原文，便于确认到底发了什么，不用去聊天记录里翻。

## 4. Client 端

### 4.1 会话入口（有内容 / 空白会话两处）

同一个组件注册在两个互补的 seat 上，因为宿主的会话 header 在空白会话里会跳过 utilities：

```js
ctx.slots.inject('conversation.session.header.utilities', () =>
  ctx.slots.register({
    name: 'conversation.session.header.utilities',
    id: 'spec-inspect-trigger',
    order: 10,
    locale: NS,
    inject: () => ({ open: () => openPicker(ctx) }),
  }, EntryTrigger))

ctx.slots.inject('conversation.hero.options', () =>
  ctx.slots.register({
    name: 'conversation.hero.options',
    id: 'spec-inspect-hero-trigger',
    order: 10,
    locale: NS,
    inject: () => ({ open: () => openPicker(ctx) }),
  }, EntryTrigger))
```

- `conversation.session.header.utilities` 是右对齐工具区，按 `order` 升序排列。`order: 10` 让它排在已有序号（-10、-5、0）之后，位于工具区最右侧，紧挨右侧边栏开关。
- **空白会话的问题**：宿主 `ConversationRoot` 里 `blank = session.blank && conversationPhase(...) === 'blank'`，`ConversationHeader` 用 `hideChrome: blank` 渲染会话 header，而 `ConversationSessionHeader` 的 `!hideChrome && (...)utilities` 把整个工具区一起跳过。所以在“新建会话、还没发消息”时，只注册 utilities 的入口完全不可见；发送第一条消息后 `blank` 变 false，入口才出现。
- **补位**：空白会话的 hero workspace 行会渲染 `conversation.hero.options`（宿主代码：`sessionId === void 0 ? null : <div className={heroOptions}>{renderSlot('conversation.hero.options', {})}</div>`）。它只在空白会话存在，正好作为“空白会话生命周期”的锚点。
- **视觉位置仍在右上角**：`conversation.hero.options` 本身位于 composer 宽度内（workspace chip 右侧），不是页面右上角。所以 `HeroTrigger` 渲染一个 `position: fixed` 的按钮，`useLayoutEffect` 里读取宿主 `[data-conversation-header-corner]`（右侧边栏开关）的 `getBoundingClientRect()`，把它放到 corner 左侧 6px、垂直居中；`resize` 与 `ResizeObserver` 时重新对齐。这样入口出现在期望的右上角，同时保留“只在空白会话出现”的语义。
- **为什么不用** `conversation.session.header.corner`：它是 `single` 槽且已被右侧边栏开关占用，注册会替换掉宿主控件（`shadows-shipped-ui`），用户会失去打开侧边栏的入口。
- 有内容后 `hero` 不再渲染，fixed 按钮随组件卸载消失，utilities 入口接管；两者不会同时出现。
- **不要占用** `conversation.session.header.corner`：那个位置是右侧边栏自己的展开按钮，替换掉会让用户失去打开侧边栏的入口。
- `locale: NS` 让组件自动拿到 `t`，不需要手动传翻译函数（hero seat 同样支持 `locale`）。

### 4.2 右侧边栏 Tab

两段注册，缺一不可：

```js
// 1) Tab 类型
ctx.sidebarRightTabs.register({
  id: 'dsh-spec-inspect/picker',
  kind: 'spec-inspect',
  priority: 'extension',
  title: () => t('panel'),
})

// 2) Tab 正文：key 必须等于类型的 id
ctx.slots.register({
  name: 'sidebar.right.pane.tab',
  key: 'dsh-spec-inspect/picker',
  locale: NS,
  inject: () => ({ api }),
}, Picker)
```

- `priority` 对页面型 Tab 不参与资源匹配，但外部插件使用 `'extension'` 语义更准确。
- Tab 类型必须先注册，`openTab(kind)` 才能找到它；注册代码在 `apply` 中同步执行。
- `ctx.inject(['sidebarRightTabs'], ...)` 是兜底路径：如果 `ctx.get('sidebarRightTabs')` 直接拿不到服务，就等 Cordis 注入后再注册。
- `openPicker` 调用 `ctx.get('sidebarRight').openTab(TAB_KIND)`；如果 Tab 类型还没就位，会短暂重试 4 次（每次 140 ms），避免“点得太早”导致静默失败。

### 4.3 页面状态与交互

`Picker` 组件维护：

- `phase`: `loading` / `ready` / `error` / `empty`
- `channels`, `warnings`, `channelId`, `docId`
- 设置抽屉：`settingsOpen`, `draftUrl`, `saving`, `settingsMsg`
- 刷新：`refreshing`
- 发起状态：`starting`, `startMsg`

首次打开：

1. `GET /status` 拿当前索引源和设置文件路径；
2. 没有索引源 → 打开设置抽屉并提示；
3. 有索引源 → `GET /index`，默认选中第一个渠道的第一篇文档；
4. 选择渠道时重置到该渠道第一篇文档。

#### 渠道 / 文档用下拉列表

渠道和文档都是自绘下拉（`Dropdown`），不再平铺展示：

- 触发器显示当前渠道名 / 文档标题，文档还带 `md` / `doc` 等类型徽标；
- 菜单项显示标题，文档额外显示 `description` 与类型徽标，选中项打勾；
- 只有一个渠道时触发器禁用（没有可选内容，仍显示渠道名）；
- 菜单用 `position: fixed` 渲染，宽度跟随触发器；下方空间不足 200px 且上方更宽时向上展开，`max-height` 按可用空间计算，因此不会被右侧栏的窄滚动容器裁剪；
- 点击外部、按 `Escape`、窗口 `resize` 或任意滚动都会关闭菜单；
- 选择文档后，若文档有 `description`，在卡片下方补一行说明。

#### 刷新按钮

标题右侧的图标按钮（设置按钮左侧）直接调用 `load(true, silent)`：

- `force = true` → 带 `?refresh=1`，绕过后端 60 秒索引缓存；
- 已有数据时 `silent = true`，保持 `phase: ready` 与当前列表可见，避免整页闪成 loading；失败才切到 `error`；
- 刷新中按钮禁用并旋转图标，`title` / `aria-label` 显示“正在刷新索引…”；
- 刷新成功保留当前渠道与文档选择；被移除的文档才回退到第一篇；
- 设置抽屉里的“重新加载索引”复用同一个 `refresh()`，所以它现在也是强制刷新。

“开始检视”按钮在无文档、无 `sessionId`、正在发起时禁用。成功后显示“已发送到本会话”，文档与选择保持不变，方便对同一文档反复检视。

#### 检视结果面板

`phase === 'ready'` 时，picker 卡片的下半部分（可滚动）展示报告：

- 状态：`report` / `reportState`（`idle` / `polling` / `ready` / `error`）、`expandedIssue`、`fixingIssue`、`appliedIssues`。
- 开始检视成功后记录 `/start` 返回的 `startSeq`，把 `reportState` 置为 `polling`；effect 每 2.5 秒请求 `/report?sessionId=…&sinceSeq=…`，拿到 `ready` 后停止并保存结果，最多轮询 240 次。
- 页面重新打开时用不带 `sinceSeq` 的 `/report` 拉最近一份报告，所以刷新页面不会丢掉上一次结果。
- 头部“重新读取结果”按钮重置 `pollFromRef = 0` 并重新进入轮询；检视仍在进行时可手动重试。
- 渲染：`dsi-report` 内先显示“检视结论”，再按级别渲染 `dsi-group`；每个分组标题是一条带底纹的横条，左侧 3px 色条按级别区分（P0 错误色、P1 警告色），分组之间用 20px 间距加 1px 分隔线隔开，避免相邻级别混在一起。条目是 `dsi-issue` 卡片，悬停时边框、背景和“定位/应用修复”按钮一起提亮，展开时保持高亮；点标题展开问题、原因、规范依据、风险、修复建议。
- 没有问题的级别显示“无”；整份报告没有任何条目时显示“本次检视没有发现问题”。

#### 定位与应用修复

- **定位**：`locateInSidebar` 组装宿主自己的文件地址 `dsh-resource://file/session/<sessionId>/<path>`，优先调用 `sidebarRight.openResourceIn(sessionId, address, { params: { line } })`，退回 `openResource`。文档预览的 text tab 读取 `params.line` 并高亮该行（`data-textpreview-line`）。
- **应用修复**：`POST /spec-inspect/apply`。发送期间按钮显示“发送中…”，成功后该条变成淡绿色勾标签“已修复”（不再可点击），同时报告区顶部出现“已发送修复请求 · 位置”卡片，可展开查看完整发送指令；失败在面板内显示原因。实际代码修改由 Agent 在会话中完成。
- 已修复状态有两个来源：本地 `appliedIssues`（本次点击即时生效）和 `/report` 返回的 `item.applied`（Host 记录并写入设置文件，刷新或重启后仍保留）。
- 按钮都在问题标题行右侧，是文字按钮：**定位**打开文件预览并高亮行号，**应用修复**把该条修复建议发给 Agent。没有 `path`/`line` 时定位禁用，没有 `fix` 时应用修复禁用。

### 4.4 为什么 Client 零 import

`client.js` 只通过宿主提供的 `require('react')` 取 React，不 import 任何 `@deepseek-ai/*` 客户端包。样式全部使用 `--dsw-alias-*` 主题 token，所以深浅色都能跟随宿主。

这样做的直接原因：桌面版迁移安装目录后，profile 里 pnpm 创建的 `@deepseek-ai/*` junction 会悬空。如果 Client 依赖这些包，插件会在加载期失败，且失败位置往往在 UI 初始化之前，很难定位。Host 端同理，所以 `index.js` 也只用 Node 内置模块。

## 5. 索引归一化

`normalizeIndex(raw, baseUrl)` 接受 Buffer、JSON 字符串或已解析对象，目标是统一成：

```js
{
  channels: [
    { id, name, docs: [{ id, title, url, type, description? }] }
  ],
  warnings: []
}
```

### 5.1 规范结构

```json
{
  "channels": [
    {
      "id": "web",
      "name": "Web 渠道",
      "docs": [
        { "id": "html-style", "title": "HTML 编写规范", "url": "https://spec.example.com/web/html-style.md" }
      ]
    }
  ]
}
```

### 5.2 兼容的变体

- 顶层直接给 `docs` 数组；
- 顶层就是文档数组；
- `channels` 写成对象映射：`{ "web": { "name": "Web", "docs": [...] } }`；
- 文档字段用 `url` / `href` / `link` / `path`；
- 渠道文档字段用 `docs` / `documents` / `files` / `items`；
- `type` / `format` 显式指定类型；
- 相对 URL 按索引源 URL 解析成绝对 HTTP(S) 地址。

### 5.3 类型推断

`normalizeType(type, url)` 的规则：

| 输入 | 归一化 |
|---|---|
| 空 | 取 URL 后缀 |
| `markdown` / `mdown` | `md` |
| `text` / `plain` | `txt` |
| `htm` | `html` |
| `word` | `doc` |
| 其他 | 原样小写 |

### 5.4 警告而不是中断

单个文档 URL 无效、非 HTTP(S)、无法解析时，不会让整份索引失败；它会被跳过并写入 `warnings`，页面在文档列表下方展示“索引提示”。只有整份索引没有任何可用渠道/文档时才抛 `empty_index`。

## 6. 文档解析

`documentText(buffer, type, url)` 是唯一的文档入口。

### 6.1 Markdown / 文本 / HTML

- 按 UTF-8 解码，去掉 BOM。
- `.html` 走 `htmlToText`：移除 `<script>` / `<style>`，把块级闭合标签换成换行，去标签并解 XML 实体。
- 含 NUL 的二进制内容直接报错，避免把乱码喂给模型。

### 6.2 `.docx`

`.docx` 是 zip：

1. 扫描 EOCD（`0x06054b50`）找到中央目录；
2. 遍历中央目录项，找 `word/document.xml`；
3. 支持 store（method 0）和 deflate（method 8），用 `zlib.inflateRawSync`；
4. 按 `<w:p` 分段，收集 `<w:t>` 文本，解 XML 实体；
5. 段落之间用换行连接。

### 6.3 旧版 `.doc`（Word 97-2003）

旧 `.doc` 不是 zip，而是 OLE 复合文档（CFB）。`wordDocToText` 的步骤：

1. **CFB 头**：校验 `D0 CF 11 E0 A1 B1 1A E1`，读 sector size、mini sector size、FAT/DIFAT/miniFAT 起点、目录起点。
2. **FAT**：先读头部的 109 个 FAT 扇区号，再沿 DIFAT 链读扩展项；把 FAT 扇区拼成一张表。
3. **目录链**：按 FAT 链读目录扇区，每条 128 字节目录项取 `name`、`type`、`startSector`、`streamSize`。
4. **mini stream**：根目录项指向 mini stream；小于 4096 字节的流走 miniFAT + 64 字节 mini sector。
5. **流**：读出 `WordDocument`、`0Table` 或 `1Table`。
6. **FIB**：`WordDocument` 偏移 0 的标识应为 `0xA5EC`；偏移 `0x0A` 的 flags 的 `0x0200` 位决定用 `1Table` 还是 `0Table`；`0x01A2` / `0x01A6` 是 `fcClx` / `lcbClx`。
7. **CLX / 分片表**：跳过 `0x01` Prc 块，读到 `0x02` 后的 PlcPcd；`n = (lcb - 4) / 12`；CP 数组加 PCD 数组。
8. **PCD**：每个 PCD 的 `fc` 带 `0x40000000` 表示压缩（1 字节/字符），实际偏移要 `(fc & 0x3FFFFFFF) / 2`；否则是 UTF-16LE。
9. **清理**：`\r`/`\x0b`/`\x0c` → 换行，`\x07` → 制表符，`\x1e` → `-`；字段指令（`0x13` 到 `0x14`）丢掉，保留字段结果；其他控制字符转空格。

压缩分片用 `TextDecoder('windows-1252')` 解码，中文正文通常是 UTF-16LE 非压缩分片。

### 6.4 误标后缀的兜底

真实环境里 `.doc` 经常不是 OLE：

- 文件头是 `PK` → 按 docx 解析；
- 文件头是 `{\rtf` → 走一个最小 RTF 文本读取器（`\par` / `\line` / `\tab` / `\uN?` / `\'hh`）；
- 看起来像 HTML → 去标签；
- 大部分是可打印文本 → 当纯文本；
- 否则返回明确的“无法解析该 .doc”错误。

### 6.5 限制

- 单文档上限 16 MB，超时 30 秒；
- 索引上限 4 MB，超时 20 秒；
- 提示词里正文最多 20 万字符，超出会截断并注明；
- PDF / Excel / PPT 不解析；
- 加密 `.doc`、Word 6/95、扫描件（只有图片）无法提取文字，会返回明确错误。

## 7. 提示词

`buildPrompt({ channel, doc, text })` 生成一条中文用户消息，包含：

1. 规范渠道、文档标题、文档地址；
2. 文档全文（带开始/结束标记）；
3. 检视对象：当前会话工作区的前端相关代码；
4. 执行要求：
   - 先通读规范、列检查项；
   - 用 `glob` / `grep` / `read` 先了解目录结构，再逐条核对；
   - 每条问题必须有文件路径、尽量带行号、关键代码证据、文档原文依据；
   - **严格按照文档定义的 P0-P5**，文档定义哪些就只用哪些；
   - 只检视、不修改文件；
   - 无问题写“无”，无法确认放“待确认”；
5. 固定输出格式：检视结论、检视范围、P0…P5 分组、级别汇总、待确认。

### P0-P5 的处理原则

- 文档定义了 P0-P5 的全部级别 → 按 P0 到 P5 分组；
- 文档只定义了部分级别（例如内部 `web-check` 文档只定义 P0-P3）→ 只输出已定义的级别；
- 文档完全没有定义 P 级 → 退回 P0（阻断）/ P1（严重）/ P2（一般）；
- 不允许模型自行新增、改名、合并或拆分级别。

## 8. 设置持久化

- 路径：`$DSH_HOME/spec-inspect.json`，未设置 `DSH_HOME` 时用 `~/.dsh/spec-inspect.json`；
- 写入方式：先写同目录临时文件，再 `rename`，避免半截 JSON；
- 优先级：插件自己的 JSON 文件 > Loader 行 `config.indexUrl`；
- 保存空字符串表示清空文件层，如果行配置有值则回退到行配置；
- 不使用 Loader patch 写用户配置：patch 层在 bundle 启用/禁用循环中不适合承载用户编辑值。
- 文件里除 `indexUrl` 外还保存 `applied`（`fixKey → 时间戳`），用于在报告里标记“已修复”。它由 `/apply` 成功后写入，最多 300 条；删除该文件会同时清空索引源与已修复记录。

## 9. 安全与边界

- 路由只挂在本地 Web 服务上，页面同源调用；插件不做额外登录鉴权，内网地址可直接配置。
- 索引源和文档 URL 仅允许 HTTP(S)；不会读 `file://`。
- `/start` 会按 `sessionId` 找**活跃** Agent；找不到就直接报错，不会创建新会话。
- 发出去的是普通用户消息，模型可以拒绝或追问；插件不注入系统提示词、不绕过权限。
- 插件唯一的写操作是保存索引源设置；检视本身只读。“应用修复”只是把修复指令发给 Agent，由 Agent 在正常会话回合里修改代码，插件自身不写工作区文件。

## 10. 取舍

### 为什么用 HTTP 路由，而不是 Typert Remote

- Remote 需要 `@deepseek-ai/dsh-typert-protocol` 等包，和“零依赖”目标冲突；
- 需要维护 marker、descriptor、codec、mount/re-mount 重试，代码量和失败面都更大；
- 同源 `fetch` 足够，且错误就是普通 JSON，调试直观。
- 代价：没有 Remote 的权限标注与统一调用面；但本插件的操作只服务于自己的页面，同源路由更简单可靠。

### 为什么没有 `spec_doc` 模型工具

- 插件把文档全文直接放进用户消息，模型不需要再调用工具取文档；
- 少一个工具就少一份 schema 校验风险（例如 `defineTool` 不接受 `required: false`）；
- 如果以后需要让模型在对话中主动换文档，可以再加一个 `ctx.tools.register` 的工具，复用同一份 index/document 读取函数。

### 为什么不用 `createUserMessage`

- `Agent.followup` 接受标准消息形状 `{ content, source }`，宿主会补 id/role；
- 少一个 `@deepseek-ai/dsh-llm` 依赖，和零依赖目标一致。
