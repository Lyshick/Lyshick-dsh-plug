# 踩坑与排查

本文记录 `dsh-spec-inspect` 实现过程中实际遇到、或差点遇到的问题，以及对应的诊断方法。大部分坑来自“插件刚装好但 UI 没出现”和“旧版 Word 文档解析”两类场景。

## 1. 客户端模块的“负缓存”导致 UI 完全不出现

### 症状

- Host 端路由 `/spec-inspect/status` 正常；
- 插件已启用，`spec-inspect` Loader 行 active；
- 页面右上角没有入口，右侧边栏也没有 Tab；
- 客户端 Slot 查询里看不到 `spec-inspect-trigger` / `dsh-spec-inspect/picker`；
- 客户端模块图 `clientModules.graph()` 里有 `dsh-quota-board`、`dsh-chat-manage`，却没有 `dsh-spec-inspect`。

### 根因

`@deepseek-ai/dsh-client-modules` 会按 **Loader specifier + owning tree baseUrl** 缓存包元数据，包括“这个包不是客户端包”的负结论。缓存生命周期是整个 Host 进程，注释写得很明确：

> Package metadata (including the negative "not a client package" verdict) is cached per Loader specifier and owning-tree base URL until restart.

本次环境里，同名插件 `dsh-spec-inspect` 曾经从另一个目录安装过，随后目录被删除，又重新安装到 `plugins/dsh-spec-inspect`。Loader 行名仍然是 `dsh-spec-inspect`，baseUrl 仍然是同一个 profile，于是客户端扫描器直接复用了旧的负缓存，根本没有重新读新包的 `package.json`。

### 诊断

在 Host 侧临时加一个状态路由，输出：

1. Loader 行是否存在、是否 active、baseUrl 是什么；
2. `clientModules.clientPath('dsh-spec-inspect')` 是否为空；
3. `clientModules.graph().entries` 里是否包含本插件；
4. 用一个已知客户端包（如 `@deepseek-ai/dsh-client-ui-sidebar-right`）验证 `clientPath` 本身可用。

典型结果：

```json
{
  "clientBundle": null,
  "knownClientBundle": "D:\\...\\dsh-client-ui-sidebar-right\\lib\\client.js",
  "clientGraph": { "count": 75, "match": ["@deepseek-ai/dsh-client-ui-chat", "dsh-quota-board", "dsh-chat-manage"] }
}
```

`knownClientBundle` 有值、`clientBundle` 为空，说明扫描服务正常，只是本包被缓存成了“非客户端包”。

### 解决

在一次性维护路由里清掉缓存并触发重新扫描：

```js
const modules = ctx.get('clientModules')
modules.pkgMeta.clear()
modules.dirty.add('dsh-spec-inspect')
modules.flush((error) => console.error(error))
```

执行后 `clientModules.clientPath('dsh-spec-inspect')` 返回真实的 `client.js` 路径，客户端模块图出现本插件，页面随后注册出入口和 Tab。

> 这段清理代码只用于本次环境的排障，**没有**进入最终插件。正常全新安装或重启 Host 后，扫描器会重新读包，不会出现这个负缓存。

### 对使用者的建议

- 首次安装后如果右上角没有入口：先刷新页面；
- 如果刷新仍没有，且这个 profile 以前装过同名插件，重启一次 DSH 即可清掉进程内缓存；
- 不要用“改包名”来绕过缓存，那会破坏安装链接和升级路径。

## 2. `@deepseek-ai/*` junction 悬空，跨包 import 会在加载期失败

### 症状

插件在 Host 或 Client 加载阶段直接报 `Cannot find module '@deepseek-ai/...'`，页面/插件行激活失败；错误往往在插件 UI 出现之前，难以定位。

### 根因

profile 的 `node_modules/@deepseek-ai/*` 是 pnpm 创建的 junction，指向**安装时**的 runtime 路径。桌面版升级或迁移目录后，这些 junction 可能全部悬空。插件如果 `import` 这些包，就会在加载期失败。

仓库里的 `dsh-web-search-ark` 早就遇到过这个问题，它的 README 明确写了“零依赖设计”的原因。`dsh-spec-inspect` 沿用同一策略：

- Host：只用 `node:fs`、`node:zlib`、`node:path`、`node:os`、`fetch`、`TextDecoder`；
- Client：只用宿主提供的 `require('react')` 和浏览器内置 `fetch`；
- 不 import `@deepseek-ai/dsh-tools`、`@deepseek-ai/schemastery`、`@deepseek-ai/dsh-typert-protocol`；
- 不声明 peerDependencies。

### 排查

```powershell
# 查看 profile 里的 junction 指向哪里
Get-ChildItem "$env:DSH_PROFILE_DIR\node_modules\@deepseek-ai" -Force |
  Select-Object Name,LinkType,Target
```

如果 Target 指向一个已经不存在的安装目录，就是这个坑。

### 取舍

- 没有 `defineTool`，所以没有模型工具；
- 没有 `Config` 的 schemastery schema，行配置按普通对象读取；
- 没有 Typert Remote，改用同源 HTTP 路由。

这些取舍的收益是：插件在 runtime 目录变化后仍然能加载。

## 3. 索引返回 Buffer，旧代码只 parse 字符串

### 症状

`spec_doc` / 索引读取报“索引里没有识别出任何渠道或文档”，但索引 JSON 本身完全合法。

### 根因

早期实现：

```js
if (typeof raw === 'string') data = JSON.parse(raw)
```

而 `httpGet` 返回的是 `Buffer`（`Uint8Array` 子类），于是 `Buffer` 走进了 `Object.entries(data)` 分支，枚举到的是字节下标，不是渠道。

### 修复

```js
if (typeof raw === 'string' || raw instanceof Uint8Array) {
  const text = typeof raw === 'string' ? raw : Buffer.from(raw).toString('utf8')
  data = JSON.parse(text)
}
```

最终实现里 `normalizeIndex` 同时接受 Buffer、JSON 字符串和已解析对象。自检里专门覆盖了字符串输入，但真实调用路径是 Buffer，所以这类 bug 必须用真实 HTTP 路由验证，不能只测纯函数。

## 4. `defineTool` 不接受 `required: false`

### 症状

插件启用时报：

```text
JsonSchemaError: unsupported JSON schema: parameters.id.required must be true when present
```

### 根因

早期实现给可选参数写成：

```js
id: {
  type: 'string',
  required: false,
  description: '...'
}
```

`defineTool` 的 schema 校验只接受“`required` 存在时必须为 true”。可选参数的正确写法是**直接省略 `required` 字段**。

### 结果

最终实现没有使用 `defineTool`（也就没有 `spec_doc` 工具），整条 schema 校验风险被移除。如果以后要加工具，记住：

```js
id: { type: 'string', description: '...' }        // 可选
action: { type: 'string', required: true }        // 必填
```

## 5. 右侧边栏 Tab 的两段注册

### 症状

点击入口没反应，或右侧栏打开后显示“无法查看此内容”。

### 根因

右侧边栏的 Tab 是两段式：

1. `ctx.sidebarRightTabs.register({ id, kind, priority, title })` 注册类型；
2. `ctx.slots.register({ name: 'sidebar.right.pane.tab', key: id }, Body)` 注册正文。

正文的 `key` 必须等于类型的 `id`。只注册正文、不注册类型，`openTab(kind)` 会找不到实现。

### 正确写法

```js
const TAB_ID = 'dsh-spec-inspect/picker'
const TAB_KIND = 'spec-inspect'

ctx.sidebarRightTabs.register({
  id: TAB_ID,
  kind: TAB_KIND,
  priority: 'extension',
  title: () => t('panel'),
})

ctx.slots.register({
  name: 'sidebar.right.pane.tab',
  key: TAB_ID,
  locale: NS,
  inject: () => ({ api }),
}, Picker)
```

### 其他细节

- 外部插件用 `priority: 'extension'`；`builtin` 是产品自带类型的语义。
- `ctx.get('sidebarRightTabs')` 和 `ctx.get('sidebarRight')` 都是 `ctx.reflect.provide` 暴露的服务，不在 Client Service 目录里，不能用 `cordis_inspect_query Service` 查“服务不存在”来判断。
- `openTab(kind)` 在类型注册之前调用会抛错。最终实现里 `openPicker` 会短暂重试 4 次，避免用户点得太早。
- 右侧栏的 `conversation.session.header.corner` 已经被“展开右侧栏”按钮占用，**不要**占这个 single slot；入口放在 `conversation.session.header.utilities` 里，`order: 10` 让它排在工具区最右侧。

## 6. 旧版 `.doc` 不是 zip

### 症状

把 `.doc` 当 docx 解析时报“不是有效的 zip 容器”，或者把二进制当 UTF-8 读出乱码。

### 根因

- `.docx` 是 OOXML zip；
- `.doc` 是 Word 97-2003 二进制格式，外层是 OLE 复合文档（CFB），正文在 `WordDocument` 流里，通过 `0Table` / `1Table` 的分片表（piece table）索引。

### 实现要点

见 [实现与架构.md](实现与架构.md#63-旧版-docword-97-2003)。最容易错的地方：

1. **扇区链**：FAT 表项不是文件偏移，是“下一个扇区号”；读数据要 `(sector + 1) * sectorSize`。
2. **mini stream**：小于 4096 字节的流不在普通 FAT 里，要走 miniFAT + 64 字节 mini sector。
3. **表流选择**：FIB flags 的 `0x0200` 位决定读 `1Table` 还是 `0Table`。
4. **CLX**：先跳过 `0x01` 的 Prc 块，再读 `0x02` 后的 PlcPcd。
5. **压缩分片**：`fc` 的 `0x40000000` 位表示 1 字节/字符，实际偏移是 `(fc & 0x3FFFFFFF) / 2`；用 `TextDecoder('windows-1252')` 解码。
6. **字段指令**：`0x13` 到 `0x14` 之间是域代码，应该丢弃；`0x14` 之后才是显示结果。

### 误标后缀

真实文件里经常遇到：

- `.doc` 实际是 docx → 文件头 `PK`；
- `.doc` 实际是 RTF → 文件头 `{\rtf`；
- `.doc` 实际是 HTML/MHTML → 含 `<html` / `<!doctype`；
- `.doc` 实际是纯文本 → 大部分字节可打印。

`documentText` 对这些情况做了顺序回退，不会一上来就报“不是 OLE”。

### 无法处理的 `.doc`

- 加密文档；
- Word 6/95 等更老格式；
- 扫描件/只有图片的文档；
- 损坏的 OLE 容器。

这些会返回明确错误，而不是把乱码喂给模型。

## 7. `immediately: true` 与页面刷新

### 症状

插件已经安装、Host 路由可用，但页面没有任何 UI。

### 原因

客户端插件默认惰性：`client.js` 执行只注册 factory，模块体在物化时才运行。没有 `dsh.client.immediately: true`，`apply` 不会自动执行，slot 就不会注册。

即使有 `immediately`，新安装的客户端插件也要等页面拿到新的模块图：

- 页面已经打开时，模块系统会通过图更新/ HMR 尝试加入新行；
- 如果页面没有更新，刷新一次页面；
- 如果页面还是旧 Host release 的模块图，需要重启 Host 或刷新。

### 排查

1. `GET /spec-inspect/status` 正常 → Host 没问题；
2. 客户端 Slot 查询看 `spec-inspect-trigger` 是否 active；
3. 如果 Host 正常但 Slot 没有，检查客户端模块图里是否有 `dsh-spec-inspect`（见第 1 节）；
4. 有图但没有 Slot，检查浏览器控制台是否有 `client.js` 执行错误。

## 8. 设置不要写 Loader patch

### 问题

Loader 的 `cordis.patch.yml` 适合部署默认值，不适合承载用户在 UI 里反复编辑的值：

- patch 层在 bundle 启用/禁用、重装、升级时可能被覆盖或重写；
- 修改 patch 可能触发整行 remount，页面状态丢失；
- 用户手改 profile 文件容易和插件管理器的写入冲突。

### 做法

- 行 `config.indexUrl` 只作为首次默认值；
- 用户设置在 `~/.dsh/spec-inspect.json`；
- 写入用临时文件 + `rename`，避免半截 JSON；
- 保存后只更新内存里的 `state.indexUrl`，下一次读取命中新 URL 的缓存键。

## 9. 内网地址与 `web_fetch`

### 现象

用 `web_fetch` 工具访问 `http://192.168.x.x/...` 会被拒绝：

```text
URL hostname "192.168.x.x" resolves to a non-public IP address
```

### 原因

`web_fetch` 是面向公网的抓取工具，会拒绝私有地址。**这不是插件的问题**。

### 验证方式

- 插件 Host 端用的是 Node 全局 `fetch`，可以访问内网；
- 手工验证可以用 PowerShell：

```powershell
Invoke-WebRequest -Uri 'http://<内网地址>/test.json' -UseBasicParsing
```

- 或者用 Node：

```powershell
node -e "fetch('http://<内网地址>/test.json').then(r=>r.json()).then(console.log)"
```

## 10. 调试 `/start` 不要误触发真实检视

`/start` 成功会调用 `agent.followup()`，真的会在会话里发一条用户消息并跑一轮检视。调试时用以下顺序，避免误触发：

1. **不存在的 sessionId + 合法 docId** → 应返回 `no_session`；验证 Agent 查找分支。
2. **合法 sessionId + 不存在的 docId** → 应返回 `doc_not_found`；这一步会先找到 Agent，再查索引，但**不会**发消息；可以证明 Agent 查找和索引读取都正常。
3. 要验证文档下载与解析，直接调用 `documentText` 或用一个临时 `dryRun` 分支；不要为了测试往当前会话发长提示词。

示例：

```powershell
$sid = $env:DSH_SESSION_ID
$body = @{ docId = '__missing__'; sessionId = $sid } | ConvertTo-Json -Compress
Invoke-WebRequest -Uri 'http://127.0.0.1:<port>/spec-inspect/start' `
  -Method POST -ContentType 'application/json' -Body $body -UseBasicParsing
```

返回 `doc_not_found` 说明已经通过了 `no_session` 检查。

## 11. 分级不要硬编码 P0-P5

内部规范文档可能只定义 P0-P3（例如 `web-check` 示例），也可能定义 P0-P5。提示词必须写成：

- 文档定义哪些级别，就只用哪些；
- 文档完全没定义 P 级，才回退到 P0/P1/P2。

如果硬编码“必须输出 P0-P5”，模型会为了凑格式编造 P4/P5 问题，或者把文档的 P0-P3 改写成 P4/P5，结果不可信。

## 12. 只读与日志安全

- 不修改工作区文件；
- 不写自定义 Session 事件。`Session.append` 的第三个参数只认 `surfaceOp` / `sourceEventSeqs`，不认 `ignorable`；自定义事件如果不带 envelope 的 `ignorable: true`，会让不认识该类型的 Harness 版本拒绝加载整份会话日志。
- 插件唯一的持久化写入是 `~/.dsh/spec-inspect.json`。
- 审计/调试信息不要写进会话日志；需要时用插件自己的路由返回。

## 13. 空会话看不到右上角入口

### 症状

- 新建会话、还没发送消息时，会话右上角没有「规范检视」图标；
- 随便发一条消息后图标才出现；
- Slot 查询里 `conversation.session.header.utilities` 的 `spec-inspect-trigger` 一直是 `active: true`。

### 根因

不是注册失败，而是宿主在空白会话里主动跳过整个工具区。`ConversationRoot` 计算：

```js
const blank = session === void 0 || conversation === void 0
  || session.blank && conversationPhase(session, conversation) === "blank"
```

`ConversationHeader` 随后用 `renderSlot("conversation.session.header", { hideChrome: blank })`。`ConversationSessionHeader` 里：

```js
!hideChrome && <div className="headerUtilities">
  {renderSlot("conversation.session.header.utilities", {})}
</div>
```

所以 `blank` 为 true 时，`conversation.session.header.utilities` 根本不会挂到 DOM，注册项 active 但不可见。发第一条消息后 `blank` 变 false，入口才出现。

### 解决

空会话改用 `conversation.hero.options` seat：它由 `conversation.content` 的 hero workspace 行渲染，条件是“有 Session”：

```js
ctx.slots.inject('conversation.hero.options', () =>
  ctx.slots.register({
    name: 'conversation.hero.options',
    id: 'spec-inspect-hero-trigger',
    order: 10,
    locale: NS,
    inject: () => ({ open: () => openPicker(ctx) }),
  }, HeroTrigger))
```

这个 seat 只提供 **生命周期**（空白会话才渲染）。位置还不够：`heroOptions` 在 composer 宽度内，图标会落在输入框上方，而不是右上角。所以 `HeroTrigger` 用一个 `position: fixed` 的容器，在 `useLayoutEffect` 中读取宿主自己的 `[data-conversation-header-corner]`（右侧边栏开关）的 rect，摆到它左侧 6px、垂直居中，并在 `resize` / `ResizeObserver` 时重新对齐。

- `hero` 只在 `sessionId === void 0 || shellPhase === "blank" && ...` 时渲染；
- 有内容后 hero 消失、utilities 出现，两处入口天然互斥，不会同时显示两个图标；
- **不要**替换 `conversation.session.header.corner`：那是 `single` 槽，已被右侧边栏开关占用，替换会让用户失去打开侧边栏的入口。

### 诊断提示

如果空会话还是看不到，先区分两种状态：

1. **有 Session、空白**（新建会话）→ 应渲染 `conversation.hero.options`；
2. **完全没有 Session**（`sessionId === undefined`）→ 宿主渲染空的 `titleRow`，两处入口都不会出现。此时没有可发送的目标会话，本插件也无处可去，属于预期。

## 14. 下拉菜单不要依赖父容器裁剪

右侧边栏是一个窄的滚动容器。自绘下拉如果用 `position: absolute`，菜单会被祖先的 `overflow-y: auto` 裁掉；把祖先改成 `overflow: visible` 又会破坏侧栏滚动。

做法：菜单用 `position: fixed`，打开时按触发器 `getBoundingClientRect()` 计算 `left` / `width`，比较上下空间后选择向下或向上展开，`max-height` 取可用空间；同时在 `mousedown`（外部）、`Escape`、`resize`、任意 `scroll` 时关闭。这样既不裁剪，也不会在页面滚动后悬空。

## 15. 报告解析不能只认一种 Markdown 写法

### 症状

- 检视明明跑完了，面板里却没有结果（`/report` 一直 `pending`）；
- 或者只解析出部分条目、位置丢失。

### 原因

提示词固定了格式，但模型仍会变：

- 字段有时写 `- **位置**：`，有时写 `- 位置：`；
- 冒号有全角 `：` 和半角 `:`；
- 多加 `分类`、`原因`、`影响` 等字段；
- 用 `## P1 问题`、`### **P2 问题**`，甚至把同一级别拆成“第一部分/第二部分”多个小节；
- 位置值写成 `` `js/game.js:124-140` ``、`js/game.js:124-140（说明）`、`src/a.vue:12`。

`parseReport` 的处理顺序是：

1. 先认级别标题（`P0`–`P5`，允许 `#`/`**` 和“问题”后缀）；
2. 再认章节标题（`检视结论`、`检视范围`、`级别汇总`、`待确认`）；
3. 条目内按字段行读取，键名做别名归一（位置/文件/行号、问题/现象、原因、规范依据、风险、修复建议/建议…）；
4. `分类` 或新的 `位置` 开启新条目，其余行作为当前字段的续行；
5. 位置值先取反引号片段，再退回正则 `path:line(-end)`。

### 注意

- 只把“出现级别标题或报告章节标题”的 Assistant 消息当作报告；其他回答不会被误认。
- 读取只走 `session.snapshotEvents()`，**不写任何 Session 事件**。
- 会话必须是 live session（`ctx.get('sessions').get(id)`）；页面关闭后读取会返回 `no_session`，这是预期。

## 16. 定位文件要用 dsh-resource 地址，不要自己滚 DOM

宿主文件预览的地址语法是：

```text
dsh-resource://file/session/<sessionId>/<path>
```

路径按 `/` 分段 `encodeURIComponent`，但保留 Windows 盘符的 `:`。打开并定位行：

```js
sidebar.openResourceIn(sessionId, address, { params: { line } })
// 或当前会话：sidebar.openResource(address, { params: { line } })
```

`params.line` 由文档预览的 text tab 读取，滚动到 `data-textpreview-line` 并高亮。不要自己查 DOM 滚动：tab 可能还没加载、文件可能是图片/二进制。

- `openResourceIn` 不在 `ISidebarRight` 的类型面上，但运行实例有；优先它，退回 `openResource`。
- 右侧栏没打开或会话未 adopt 时，调用可能静默无效——先确认 `ctx.get('sidebarRight')` 存在。
- 定位只是打开文件，不修改文件。

## 17. 应用修复的边界

“应用修复建议”不是插件直接改文件，而是：

```text
POST /spec-inspect/apply → buildFixPrompt(item) → agent.followup(...)
```

这样做的原因：

- 修复需要读上下文、判断改法，只有 Agent 能做；
- 修改会走正常的会话回合、权限与审批，和用户自己发指令一致；
- 插件仍然只写自己的设置文件，回滚与审计都留在会话日志里。

注意：

- 每条问题单独发送，避免一次改太多；
- `path`/`line` 缺失或 `fix` 为空时直接拒绝，不会发消息；
- 会话正在跑上一轮时 `followup` 可能失败，页面会显示原始错误。

## 18. `followup` 的消息缺 `id`/`role`，聊天里看不到用户气泡

### 症状

- 点「应用修复」后，AI 确实开始工作了，左栏也出现了修复回合；
- 但聊天流里，上一轮“已完成”和这一轮的 AI 回复之间**没有用户消息框**，看不到自己“发出”的修复建议；
- 同样，`/start` 发出的规范全文也没有出现在聊天里。

### 诊断

会话日志是 zstd 多帧压缩的 NDJSON，逐帧解压后对比 `user/message` 事件：

```text
插件发的消息： dataKeys = content,source          id = (none)   role = (none)
正常注入消息： dataKeys = content,source,role,id   id = <uuid>   role = user
```

同一次会话里两种形状并存，说明问题不在会话存储，而在插件发送的消息本身。

### 根因

`Agent.followup` **不会**补 `id`/`role`：

```js
followup(input) { this.send(input, "next-turn", true) }
...
this.session.append("user/message", message, { surfaceOp: "append" })
```

它只是把对象放进 inbox，loop 在 step 时原样 append。Chat 的消息投影用 `event.data.id` 认领消息（`String(event.data.id)`、inbox claimed 集合），缺 `id` 的 user 事件会被静默跳过——事件在日志里、模型也收到了，但界面不渲染。

### 解决

发送完整的 `UserMessage`：

```js
{ id: randomUUID(), role: "user", content: [{ type: "text", text }], source: { kind: "user" } }
```

`userMessage()` 同时用于 `/start` 和 `/apply`。修复后日志里的新事件应带 `role: "user"` 与 UUID `id`，聊天中出现普通用户气泡。

### 排查提示

如果以后再接入别的“程序发送消息”路径，先检查这条事件是否带 `id`/`role`；只看“AI 是否响应”会误判为发送成功。
